# Sunday 18 October 2026 — preserve, learn, then decide

This is today's proposed checklist, not a record of completed work. At inspection,
`q/` resolves to the live Qubigo repository on `feature/004-competitions`. The
factory lives in Libby; fixing its parser is work in that repository. The new
implementation attempt is provisionally called `004a`; choose its exact factory
run identifier explicitly before launch (for example `qubigo-004a`).

## Checklist

- [ ] **Preserve open Qubigo work on its current branch.** Inspect the complete
  diff and untracked files, exclude generated files and secrets, then commit the
  intended work on `feature/004-competitions`. Record the commit here. Label its
  validation status honestly: preserving unfinished work does not accept task 7.
- [ ] **Extend the analysis with five whys.** Trace at least two separate chains:
  why the factory could not read the result, and why repeated repairs increased
  complexity without establishing the production contract. For each why, attach
  evidence, distinguish a hypothesis from an observation, and identify what would
  disprove it. Do not force five levels when the evidence ends earlier.
- [ ] **Capture findings in Qubigo's kaizen ledger.** Write or extend focused notes
  under `q/docs/kaizen/` and update `q/docs/kaizen/README.md`. Separate machinery
  causes from product design choices. Record proposed countermeasures and how
  their effect will be checked; do not mark proposals resolved. Decide which
  branch should hold these notes so they remain available after returning to main.
- [ ] **Fix the factory's latest unreadable doer result.** Work in Libby. A Markdown
  answer with no JSON differs from fenced JSON. Define a bounded recovery policy
  and a clear final failure; preserve raw evidence and prohibit acceptance from
  prose alone. Add a meaningful regression for no-JSON output, run the appropriate
  factory checks, and commit the correction separately from Qubigo changes.
- [ ] **Return Qubigo to main deliberately.** Confirm the preservation commit and
  clean working tree before switching. Inspect what main already contains and
  carry over only the intended analysis or improvements; do not merge the entire
  unfinished competition implementation as a shortcut.
- [ ] **Apply the most important learnings on Qubigo main.** Rank them by likely
  impact, select a small number, and state how each prevents the observed failure.
  Prefer a concrete design-guidance or validation improvement to more blanket
  instructions. Verify and commit each coherent change. If the key learning is
  to change implementation guidance, demonstrate that change before another run.
- [ ] **Decide whether 004a is ready.** Agree a short collaboration sketch, what
  accepted work is retained, and the first observable acceptance boundary. Record
  what changes from 004 and what would cause an early stop. Preserve the same
  product requirements unless deliberately revised with an explicit rationale.
- [ ] **Try iteration 004 again as a fresh 004a run.** Use an isolated Qubigo branch
  from the chosen main baseline, a fresh run identifier and plan, and the existing
  iteration-004 seed. Do not overwrite 004 evidence. Inspect the first vertical
  slice before authorizing the whole iteration; compare the result against the
  stated learning goals, not just passing tests or completed checkboxes.

## Challenge to this plan

**What would starting again buy that a targeted refactor would not?** The failure
is not yet evidence that all tasks 1–6 or every added abstraction should go.
Name the smallest change in design ownership that would make one complete game
understandable. Compare keeping and simplifying the existing work with rebuilding
that slice before deciding on a rewrite.

**Why should 004a behave differently?** A new name, a parser fix and a longer
prompt leave the same design feedback loop in place. Choose an observable
improvement: for example, a short responsibility sketch that matches the actual
command path, and one full-game example that records a result through real wiring.
Check those before accumulating cutoff and recovery machinery.

**Are we explaining the cause or blaming the model?** “The model ignored JSON”
explains the immediate stop, not why a single response-format failure loses the
handoff. Likewise “tests passed” says little if they omit the collaboration at
risk. Keep the five-whys chains separate and ground countermeasures in evidence.

**Can today's scope fit a learning cycle?** Preservation, root-cause analysis,
factory repair, main-branch improvements and a fresh feature implementation are
several substantial activities. A good stopping point today may be preserved
work, evidence-backed countermeasures and an agreed first experiment. Launching
004a is conditional on readiness, not today's success criterion.
